# P2-3 · 分发补强评估

> 来源：`芙洛理·桌面客户端优化清单.md` 三、P2-3
> 原文动作：评估桌面端分发短板（无应用商店、Windows-only），对比 WebView/跨端方案补分发；不盲目做完整移动 App。
> 验收：给出"桌面为主、跨端为辅"的分发方案与成本估算。
> 工作量：1 pd（评估）｜ 依赖：P2-1

---

## 1. 当前分发现状（事实，非设想）

| 维度 | 现状 | 短板 |
|---|---|---|
| 形态 | 原生 Win32 + D3D11/D2D 自绘，**零第三方依赖** | 仅 Windows 可运行 |
| 运行依赖 | 需自带 `Server/`（Node 服务端，REST 8787 + WS）做云端 | 纯单机可跑，但"云同步/自习室/好友"需服务端 |
| 安装 | 目前是原始 `Flori.exe` + 资源目录手动拷贝 | 无安装器、无签名、无商店入口 |
| 信任 | 无代码签名 | SmartScreen / 杀软会拦截，首次打开报警 |
| 更新 | 手动替换 | 无自动更新通道 |
| 跨端 | 无 | 移动端完全空白 |

结论：**分发是桌面端当前最大短板，且与"零依赖原生"的技术选择强绑定**——要跨端就得动架构，成本陡增。

---

## 2. 方案对比（桌面为主、跨端为辅）

### 方案 A · 加固桌面分发（推荐，优先级最高）
- 打 **InnoSetup / NSIS 安装包**，一键装到 `Program Files`、建开始菜单/卸载项。
- **代码签名**：普通 SHA-256 代码签名证书（~¥1.5k–3k/年）消除"未知发布者"；EV 证书（~¥3k–6k/年）可加速 SmartScreen 信誉积累、免首次报警。
- **自动更新**：客户端加一个 `CheckUpdate`（拉 `Server` 版本端点 + 增量 patch），后台线程下载、下次启动应用（沿用现有"UI 线程不碰网络"约束）。
- 可选 **Microsoft Store（Win32 桥接）**：提交打包的 Win32，获得商店入口与自动更新；审核对系统库白名单友好（已零依赖）。
- **成本**：安装器 0.5 pd（社区脚本现成）；签名证书年费；自动更新 1–2 pd；Store 上架 1 pd（审核等待另计）。**合计约 3–5 pd + 证书年费。**

### 方案 B · 轻量 Web 伴侣（跨端为辅，不重写客户端）
- 归档的 `WebApp/`（纯前端 + localStorage，已在 `封存/`）可复活为**只读伴侣**：手机上看路线图/专栏/成就，桌面端仍是主战场与写入端。
- 用 **PWA**（Service Worker + 清单）包一层，手机"添加到主屏幕"即得类原生入口，**零原生开发**。
- 局限：只读、不与桌面端实时双向写（真·多端写入需服务端账户维度，P2-1 已证明数据按账户隔离可聚合）。
- **成本**：PWA 壳 1 pd（基于现有 WebApp）；若要和桌面端共享服务端数据，需 `Server` 暴露只读聚合端点 1 pd。**合计约 2 pd。**

### 方案 C · 跨端重写（Tauri / Flutter / Electron，不推荐现阶段）
- 把原生 UI 换成跨端框架才能"一份代码多端"。但本客户端核心是 **D3D11 纸纹渲染 + 手写 WS + Win32 EDIT IME 代理 + 系统托盘**，这些全是 Windows 专属深层能力，跨端框架要么重写、要么退化成 WebView 壳（失去"零依赖原生"护城河）。
- **成本**：等效重做客户端，数月级（20+ pd），且动摇 P1-5 护城河。**仅当 P2-1 验证出移动端强需求才考虑。**

---

## 3. 推荐路线（桌面为主、跨端为辅）

```
现在 ──► 方案 A（签名安装包 + 自动更新 + 可选 Store）
            │  解决"无商店/不信任/难装"三痛，保住原生护城河
            ▼
并行 ──► 方案 B（PWA 只读伴侣，手机看路线/成就）
            │  低成本补"跨端可达"，不碰写入端
            ▼
门控 ──► 方案 C 仅当 P2-1 次日/7日留存 + 移动端强诉求成立才启动
```

**为什么不是先跨端**：清单明确"不盲目做完整移动 App"。桌面原生是已验证的差异化（P1-5 护城河、F3/F4 留存抓手），分发短板用 A+B 即可补到"能用、可信、可更新、手机能看"，不必为跨端重写动摇根基。

---

## 4. 成本估算汇总

| 方案 | 工程量 |  recurring 费用 | 风险 |
|---|---|---|---|
| A 加固桌面 | 3–5 pd | 代码签名证书 ¥1.5k–6k/年 | 低（沿用现有架构） |
| B Web 伴侣 | ~2 pd | 静态托管（可选） | 低（只读，不碰写入） |
| C 跨端重写 | 20+ pd | 高维护 | 高（动摇护城河） |

> 全部成本以"不新增第三方依赖、不削弱原生体验"为前提；证书费用为市场公开区间，实际以采购为准。

---

## 5. 与 P2-1 的衔接

- P2-1 真机"百级留存曲线"必须有分发渠道才能凑样本 → **方案 A 是 P2-1 验收的前置工程**。
- 若 P2-1 给出 go（移动端强需求），再评估方案 C；若 no-go，停在 A+B 即可。
- 故执行顺序建议：**P2-3 方案 A 落地 → 回流 P2-1 采集 → 视结论决定是否碰 C**。

---

## 6. 结论

- 已给出"桌面为主、跨端为辅"的明确分发方案（A 为主、B 为辅、C 门控）。
- 成本清晰、风险可控，**不盲目跨端重写**。
- 下一步建议：先落方案 A 的签名安装包（消除"不信任/难装"），并行方案 B 的 PWA 只读伴侣；方案 C 等 P2-1 数据门控。
